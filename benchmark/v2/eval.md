# V2 evaluator procedure

Evaluator-only. Read the matching pinned `prompt.md`, `assessment.md` and `criteria.json`. The candidate sees the complete outcome and point breakdown, not this procedure or other runs. V1 remains frozen and is never scored with V2 rules.

1. Validate identity and revision against the operator-owned attempt record. Check the frozen artifact manifest, start/deadline/completion timestamps, terminal state and declared sessions. Invalid procedural runs are recorded with evidence and excluded; do not repair or rerun them. All later checks are evaluator evidence.
2. Use an evaluation copy or a recorded evaluator workspace. Do not edit candidate source or candidate evidence. Install from its lockfile using the corresponding frozen-install command; capture logs and installed versions. Compare dependency majors with the recorded attempt-start baseline, not current npm versions. Missing baseline evidence keeps dependency evaluation pending. Confirm the adapter's installed version supports the chosen Astro version using official documentation/package peer dependencies.
3. Run the declared production build and local Workers production preview on a free, unique loopback port. Confirm process ownership and page identity before checking it. Do not serve an unrelated build or use a plain static server as proof of Workers runtime. No public deployment or cloud credentials. Inspect actual generated/explicit configuration, asset entrypoints, compatibility settings and required bindings; compare them with README commands. A package dependency alone does not prove an activated adapter.
4. Request all seven routes and inspect navigation, genuine content, meaningful route-specific HTML and metadata. HTTP 200 for a fallback error page does not pass. Record each route and the number passing the relevant proportional checks. Check both requested viewport widths, keyboard navigation, image alternatives and original links. Verify every selected unique media ID and source identity; compare actual publication dates to the attempt-time window. Preserve source evidence. Do not infer authenticity from plausible titles. Provider/network errors are not proof of fake content.
5. Trace fetching from dedicated server-side modules through normalized data into presentation. Inspect both successful retrieval and a controlled timeout, HTTP failure or malformed response. Use the candidate's supported seam or test source in an evaluator copy; record any instrumentation. Do not silently modify the submitted implementation to make it pass. A graceful empty state alone does not prove authentic media retrieval.
6. Score each subcheck from the public breakdown. Binary checks are zero or their full maximum. Route checks are `max * passingRoutes / 7`, rounded to two decimals. Category totals are the sum of their subchecks rounded to two decimals. The nine category maxima sum to 100. Never invent deductions or substitute assessment sequence for outcome quality.
7. Build failure does not halt the whole evaluation. Set the failed build and unavailable runtime subchecks to zero with the build log. Continue inspecting independently verifiable pages/source boundaries, installed dependencies and candidate self-verification. Historical failed tests can still prove honest candidate verification, but never successful final runtime. Evaluator infrastructure outages leave affected checks pending rather than blaming the candidate.
8. Request explicit human scores/notes for consistent UI and desktop/mobile usability, giving the owned preview URL and the public definitions. Preserve reviewer and timestamp. Do not infer human approval from an agent screenshot. If the user is unavailable, save a draft; do not publish numeric default scores. For runtime unavailable due to a proven candidate build failure, record zero and the failure evidence instead of requesting fictitious visual acceptance.
9. Validate `evaluation.json`: exact version/identity/revision, every criterion and subcheck exactly once, expected maxima, finite scores within allowed values, evidence files present, correct evidence origins, required manual confirmations, and no pending check in a finalized result. Candidate-verification checks require pre-completion candidate artifacts. Evaluator tests cannot fill these slots. Missing evidence remains pending or earns zero only when its absence is the observed candidate outcome.
10. Finalize only after every required check has a resolved outcome and valid evidence. Generate display totals/CSV from the structured result. Keep draft and invalid records inspectable but outside published data. Stop only evaluator processes you own, after manual review or a recorded handoff. Never execute a new paid attempt as part of scoring.

## Result contract

Operator `attempt.json` and evaluator `evaluation.json` share `(benchmarkVersion, attemptId, benchmarkRevision)`. `evaluation.json` contains `status` (`draft`, `final`, `invalid`), `checks`, evaluator identity/timestamp and optional cost/screenshot attribution. Each check contains `id`, `status` (`pending`, `scored`), `score` (null while pending), explanatory `notes`, and evidence references with `origin` (`candidate`, `evaluator`, `human`). Human records include reviewer and UTC confirmation time; build-failure substitutions identify the failing build evidence. Evidence paths are relative to their owning recorded artifact root, cannot escape it, and must resolve to existing files. A freeform claim without evidence is not a finalized result.

No CSV from unversioned `eval-results/` is a V2 result. Do not infer benchmark version from model name or reuse a V1 identifier without its version. The result validator and processor must reject wrong versions, duplicate identities, unknown/duplicate/missing checks, invalid scores and inconsistent revisions before generating any public output. Pending records are excluded. V2 metadata cannot modify the frozen V1 snapshot or its API.

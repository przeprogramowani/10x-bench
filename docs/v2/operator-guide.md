# Operating V2

V2 migration creates no model runs. For a separately requested campaign:

1. Add the requested model to `benchmark/models-v2.json`, keyed by model ID, with `name`, `environment`, exact harness/model settings and optional verified pricing. Keep unknown costs null. Do not edit V1 metadata. Decide the requested number of attempts; no automatic replay of V1.
2. Verify the benchmark bundle. Use the launch skill to prepare fresh versioned candidate/result directories. Operator `attempt.json` stores the fields in `benchmark/v2/run-protocol.md`. Save full registry responses in the result directory and baseline entries with `version`, `major`, `publishedAt`, `capturedAt`, and relative `reference` pointing to that response. `stableReleaseAtStart` in `scripts/dependency-baseline.ts` resolves stable releases by publication time. Capture immediately before launch and record the absolute 60-minute deadline.
3. Give the candidate the complete prompt, assessment and baseline. Keep operator files outside its directory. Use native goal mode where supported; otherwise only neutral continuation with the same deadline. Record session IDs, canonical cwd, interruptions and terminal state. No publication or credentials. Paid launch must be authorized by the campaign request.
4. At termination, freeze source and candidate verification files with hashes. `artifactHashes` maps candidate-relative evidence paths to SHA-256. Candidate evidence references have `capturedAt` within the run; later evaluator evidence cannot earn candidate points. Operator capture should retain the entire implementation manifest as well as referenced verification files.
5. Follow the scoring skill and matching evaluator protocol in an evaluator copy. `evaluation.json` uses `status: "draft"` while any required check is pending. Use every ID from `criteria.json` exactly once. `evaluator` contains `name` and UTC `completedAt`; `checks` have `id`, `status`, `score`, `notes`, and `evidence`. Binary scores are zero/full maximum; route checks also record `passingRoutes` from 0 to 7. Evidence has `origin` and a relative file `reference`; human evidence also has `reviewer` and `confirmedAt`. Candidate evidence has its capture time and matching frozen hash. Document genuinely absent candidate evidence with score zero, `absentCandidateEvidence: true` and evaluator evidence. A build-failure zero on unavailable manual checks uses `unavailableDueToBuild: true` and evaluator build evidence. The original candidate artifacts stay untouched.
6. Ask the human reviewer to inspect the owned preview for consistent UI and both desktop/mobile views. Preserve notes and confirmation times. Finalize only when every required check is resolved. Invalid procedural runs remain recorded with `status: "invalid"`; drafts/invalid records do not rank. A failed build does not erase independently earned source/dependency/self-verification scores.
7. For OpenCode costs run `npm run calculate-cost -- <attempt-id>`; add `--write` to save cost into its V2 evaluation. The read-only database lookup counts only recorded candidate session IDs with matching canonical cwd, excluding later manual sessions. The supported record shape uses `sessions: string[]`; missing sessions fail instead of becoming free usage.
8. For screenshots, use the evaluator-owned local preview: `npm run screenshots -- <attempt-id> <preview-url> <unique-visible-text>`. The identity string must come from that attempt's rendered source. The tool checks status/identity, writes only V2 images and creates that V2 model's filmstrip. It does not install/build/mutate candidate code. This capture is evaluator evidence, not candidate verification or human acceptance.
9. Run `npm run process-results` and inspect the output. It rejects malformed final records, preserves V1 and generates V2 data/API from final records only. Finalized records retain their benchmark revision; an unknown older revision fails with a request for its matching rubric rather than being regraded with current rules. Multi-revision ingestion requires retaining the corresponding bundle before such a campaign; the initial migration has one V2 revision.
10. Review generated changes, then publish through the separately authorized release process. No candidate run or publication is performed by the empty-dashboard migration.

Model metadata is preparation input. Each attempt freezes its own model name/environment, and aggregation rejects conflicting attribution for the same model ID. A changed model/environment needs a distinct ID. The initial V2 dataset has no supersession entries; never reuse V1 supersession mappings.
